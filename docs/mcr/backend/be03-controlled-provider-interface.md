## Private provider and issuance interface

Use Google OIDC as the first positive case because it traverses both token and userinfo requests. Apple remains a distinct token/ID-token and form-post qualification; do not fabricate an Apple userinfo request. X's BasicAuth/XApiV2 path also remains separately scoped unless explicitly assigned.

The provider fixture is private, per-run and loopback-bound. It must not become a public development login endpoint. A test-only authorize handler receives the actual Auth-generated redirect/state/challenge/nonce and generates an unpredictable one-use authorization code bound to that tuple and a private case ID/subject. It stores an expiring grant; there are no preknown parity codes and no arbitrary caller-supplied identity assertions. The token handler atomically consumes the grant and validates client authentication, exact redirect and S256 verifier before returning a fresh access token and signed RS256 ID token with the matching nonce/issuer/audience/subject/expiry. Userinfo validates that issued bearer token and returns the same subject. Fresh signing material and synthetic client credentials are fixture-only and never real-provider credentials.

Keep the production `HttpOAuthProviderClient` implementation intact. The initial fixture constructs it directly with explicitly isolated HTTP endpoints and builds the real OAuth use case through existing public APIs. Its generic URL validator permits hosted URLs; that does **not** mean production AppConfig accepts loopback or HTTP. Record the fixture mode/composition in every receipt. Full production HTTPS configuration/startup remains `NOT_RUN`; do not add a production loopback exception, hostname trick, placeholder allowlist, disabled certificate verification or operator bypass. A later HTTPS controlled deployment must satisfy unchanged AppConfig and have separately assigned origin/TLS/provider custody; it is not a prerequisite invented for this bounded fixture claim.

There are two separate issuance observations: (1) the controlled provider's private one-use authorization-code issuance and exchange, and (2) Auth's actual signed access/refresh token pair plus persisted canonical identity/session. Neither can substitute for the other. Gateway success must retain its protected refresh cookie, then an authorized browser `POST /api/auth/refresh` must yield the canonical identity using that cookie. Do not return tokens through redirect URLs or claim a lookup-only identity is issuance.

## Observation interface and deterministic scenarios

Use an in-process test control handle, not a production HTTP control endpoint, to select a scenario and release barriers. Journal monotonically sequenced events `{run, case, component, phase, elapsed, active_count, outcome}` with private noncredential correlation handles. Enter request-start/RAII flight tracking at the outer HTTP service boundary **before** form/body parsing, code lookup, authentication or any await that can cancel. Track token and userinfo independently; track actual Auth callback RPC entry/exit with a test transport layer. Completion-only counters cannot prove absence of requests. Record starts, successful completions, errors and dropped flights separately.

Never log raw codes, state, nonce, verifier, client secret, bearer/refresh/access tokens, private keys or provider response bodies. Use per-run redacted handles and bounded event buffers that fail on overflow. Raw test-only values may remain in memory for assertions and final leakage scans; they must not enter durable receipts. SQL effect checks are test-owned and scoped to the fresh fixture databases, never a reused operational lease.

| Case | Required deterministic observation |
| --- | --- |
| Positive first/repeat login | Actual authorize RPC creates unconsumed state; private code issued; at token request-start, owning PG shows state already consumed. Exactly one token and one userinfo request; canonical user/identity/session/login audit and exchange SUCCESS match. Repeat login preserves canonical identity without duplicating its provider identity. Refresh cookie POST resolves that same identity. |
| Cookie/state/provider/tamper/duplicate-field rejection | Selected Gateway rejects before actual callback RPC; zero new token/userinfo starts and zero identity/session effects. Assert exact per-case deltas, not aggregate totals. Callback-supplied returnTo never changes the bound target. |
| Provider access_denied | Valid bound cookie/state produces denied 303 and clears state cookie. Zero callback RPC and provider starts; no identity/session/exchange audit. Auth state is not consumed by this Gateway-only branch; it expires normally. Do not falsely claim durable denial tombstoning. A stolen/restored old signed cookie before expiry is outside a zero-Auth denial-consumption guarantee and needs an explicit contract decision if required. |
| Expired state / replay / concurrent duplicate callback | Use a fresh valid Gateway cookie with controlled owning-state expiry, or barriers for concurrent callbacks. Actual PG consume rejects expiry/reuse; only one concurrent callback can exchange. Replay after a failed, timed-out or completed exchange adds zero token/userinfo starts and no session. Keep Gateway cookie expiry distinct from Auth state expiry. |
| Token error or invalid code | Start recorded even when parsing/auth/code lookup fails. No userinfo start, no session/identity creation; state remains consumed. Exchange FAILURE audit is required when the use case returns through its post-await error path. No automatic retry. |
| Userinfo error / mismatched subject / invalid nonce | Observe the actual stage reached. Userinfo error requires token success and userinfo start; invalid nonce must fail before userinfo. No canonical session/identity issuance; consumed state blocks replay. |
| Token in flight, callback caller cancelled or deadline expires | Wait for token-start barrier, observe consumed state, cancel the actual caller or exhaust its deadline, then observe every component through bounded drain. Distinguish returned HTTP error from actual task cancellation. Record eventual exits/dropped flights and final database state; if issuance occurs after caller abandonment, report/fix it rather than claim cancellation succeeded. |
| Userinfo in flight, callback caller cancelled or deadline expires | Release successful token response, wait for userinfo-start, then cancel/time out. Require separately bounded actual RPC/provider drain and no late session issuance for the intended guarantee. A fixture server may finish its own handler after client disconnect; server completion is not proof Auth remained active. |

Use explicit start/release channels and bounded timeouts rather than sleep-based races. If the selected transport does not propagate cancellation, preserve that finding and measure the request-budget ceiling; do not manufacture an exchange audit for a dropped future. Source records audit after the await, so an actually cancelled future may have no exchange audit. Missing completion/audit alone is neither evidence of no request nor of safe termination. Tests must inspect zero active flights, joined server tasks, released listeners and post-drain DB deltas before asserting no late effects.
