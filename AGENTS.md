# MCR working agreement

## Authority and delivery

- The user's delivery repository is `julymeltdown/mcr`, branch `master`. Old references to delivery into Bigyeting in `docs/source/` are historical, not instructions for this repository.
- Read `MCR_IMPLEMENTATION_PLAN_V2_EN.md`, `docs/mcr/project-assessment.md`, and `docs/mcr/execution-plan.md` before implementation. Product scope and acceptance come from the specification; analysis documents do not silently amend them.
- Preserve `docs/source/` byte for byte. Record provenance for copied code, source revisions, destination paths, dependencies, and regression evidence.
- Use English only in every chat/session, including other development chats: replies, progress updates, questions, reviews, handoffs and final answers, even when the user writes in Korean. Carry this explicit user instruction into delegated or continued chats. Use English for new chat titles, product navigation and engineering artifacts. Preserve exact source text, filenames, identifiers and quoted evidence where fidelity requires it.

## Parallel work and delivery

- Two equal `mcr(king)` chats coordinate major feature delivery and shared decisions. Functional `mcr(sl)` leads manage feature context, dependencies and worker allocation. Developers own all implementation validation, including code, queries, tests, runtime evidence and fixes. Kings and SLs must not inspect, review or validate implementation or queries, rerun tests, or impose a separate QA, review or approval stage. Track progress through delivered behavior, periodic commit-log checks and actual chat activity. Reuse idle chats for ready related work; archive finished chats with no next assignment after preserving their work. Reporting idle status alone is not resource management (explicit user direction, 2026-11-04). See [current ownership](docs/mcr/king-coordination.md).
- A king receiving a review or verification request must decline: "I don't perform reviews. The responsible developer owns validation; please resolve this with the implementation owner." SLs likewise do not review code, queries or tests. No work waits for king or SL review. Staffing, priority, ownership conflicts and missing product decisions may still be escalated.
- The user explicitly requires separate visible Codex chats for backend and frontend development, not a subagent-only arrangement. Use the authorized chat-management tools, keep each writer on its assigned isolated worktree, and stop the former writer before transferring ownership. A designated delivery chat integrates validated handoffs without waiting for main-chat or scrum-lead approval.
- Preserve the user's selected model and reasoning setting in each chat. The user withdrew the earlier fixed `gpt-6.1-sol` / `high` requirement; omit model and reasoning overrides from coordination and continuation calls unless the user explicitly requests a new setting. Prefix chat titles with `mcr(king)`, `mcr(sl)`, `mcr(be)`, `mcr(fe)`, `mcr(qa)`, or `mcr(art)` as appropriate; title failure must not block work.
- The user explicitly requires a persistent goal in each assigned development chat. Every assignment must include a concrete objective and completion criteria covering implementation, relevant validation, documentation, committed handoff, and developer-owned validation fixes. Ask the receiving chat to inspect its current goal and create one when no unfinished goal exists; reuse an aligned active goal and report incompatible goals without falsely completing them. Continue until the assigned scope is delivered, keep unfinished required work active, and verify actual goal status rather than treating a sent instruction as proof. Do not set a token budget unless the user requests one.
- Give each worker explicit task IDs and disjoint file ownership. Workers do not change central manifests, lockfiles, contract registries, root routers, or CI composition without coordination with the integrator.
- Start a task when its actual prerequisites are satisfied. Do not impose full-wave barriers or make FE feature implementation depend on matching BE feature completion; use frozen contracts and deterministic fixtures.
- Implementation owners choose and perform all necessary verification, resolve technical interfaces directly with the relevant implementation owners, fix failures and deliver committed handoffs. Real vertical-flow gates remain required; there is no separate king, SL or QA verification or approval stage. Reassign or close idle, finished, duplicative, or conflicting agents. Reuse context when a follow-up is closely related.
- The publishing developer named in the current assignment publishes the implementation owner's validated scope. Where an existing assignment names a delivery integrator, use that handoff directly; this is publication routing, not king/SL inspection or permission. This policy does not silently transfer publishing or shared-file ownership. Use explicit staged paths, preserve concurrent work, reconcile remote history, and never force-push. The publishing owner resolves non-fast-forwards, runs relevant combined checks and verifies remote delivery. No king acknowledgment or ledger update is a prerequisite. Never share a writable checkout.

## Instruction freshness and handoff routing

- The latest human no-review direction overrides obsolete parent/main/king/SL review or acknowledgment clauses in old goals, assignments and worktree copies. Those clauses are not unfinished product requirements. Keep all original implementation, validation, fixes, documentation and publication duties; preserve truthful goal metadata and do not reset or falsely complete a goal.
- On every resumed or transferred assignment, the lead carries this override explicitly. Preserve frozen source and historical evidence; do not mass-rebase or edit peer worktrees merely to refresh instructions. The receiving owner applies a safe documentation-only policy refresh when its source/ownership boundaries permit it. An old checkout does not restore an obsolete review gate.
- Routine code, query, screenshot and test handoffs go to the responsible implementation counterpart or named publishing developer. Do not send a king a packet to inspect, verify, approve or acknowledge. Kings receive hourly major-feature outcomes, task states, owners, commit references and genuine ownership/product exceptions. Progress accounting consumes the responsible-owner/SL disposition; kings do not independently reinspect its technical evidence.
- Distinguish pending developer validation, waiting for a resource slot, waiting for publication and an actual ownership/product blocker. Never label those states as awaiting king review. Publication and a worker's next ready assignment do not wait for the central ledger.
- Resource allocation is capacity scheduling, not a technical approval stage. The allocator gives a usable bounded validation round; the developer can diagnose, repair and rerun within its accepted lease, scope and limits without another king/SL correctness decision. Current deadlines, cleanup, byte limits and fair queues remain binding. Expired or insufficient offers require release/requeue; this is not permission for an implicit extension or unallocated workload.

## Frontend/backend separation

- Give every implementation worker its own Git worktree and task branch, such as `codex/mcr-be-BE03` or `codex/mcr-fe-FE09`. Concurrent workers must not edit the integration worktree or share a writable checkout, including workers within the same lane.
- Backend workers write only their assigned paths under `backend/`; frontend workers write only their assigned paths under `frontend/`. Lane-specific documentation may be explicitly assigned separately. Reading the other side for compatibility review does not grant permission to modify it.
- The delivery integrator coordinates single-writer ownership of shared HTTP/realtime/asset contracts, generated artifacts, central manifests and lockfiles, root composition, CI, and infrastructure. It may delegate an exact shared-file scope to an implementation owner and record the transfer; shared changes must not wait for main-chat or scrum-lead approval. No worker acquires these paths implicitly. This includes `backend/docs/api/` and `backend/proto/`.
- Frontend code must not import backend implementation files, server configuration, database access, or secrets. Backend code must not depend on frontend rendering, browser state, or frontend mocks. Connect through the agreed HTTP/WebSocket contracts and generated public types. Client validation does not replace server authorization or invariants.
- Split work spanning both sides into separate backend and frontend patches/commits. QA and art workers receive exact test or asset paths; their assignments do not grant general application-code ownership.
- The publishing owner checks changed paths and cross-directory imports against its assignment, records its base and delivered commits, and runs relevant combined checks. Return out-of-scope edits to the responsible lane or request an explicit ownership transfer. These checks do not require another king/SL review. Implementation owners resolve remaining validation concerns themselves; kings and SLs do not inspect or validate the implementation or queries.

## Implementation boundaries

- All rendering/UI is newly authored. Only audited headless Bigyeting logic may be reused; keep old rendering and unneeded visual libraries out of the new application.
- The latest [ten-screen visual target](docs/mcr/design/reference-target-2026-11-04.png) is an exact component/design target, not loose inspiration. Match its layout, proportions, typography, dense rows, imagery, icons and controls in functioning application components. Palette/frame adoption alone is insufficient. Preserve the original image; do not substitute a static screenshot for working UI. Actual states/data remain truthful and server-authorized. Compare native 360/390/430px captures against the target; visual acceptance remains open while material differences remain.
- Character artwork must come from the user's selected [source pack](frontend/src/entities/avatar/character-source-pack.json) and its reviewed derivatives. Previous/legacy character images are prohibited, including fallback images. See [character-source guidance](docs/mcr/character-art.md). The C06 synthetic fixtures are metadata tests, not approved product art. Preserve supplied originals byte for byte and do not silently replace them with newly generated designs.
- Never use decorative left accent lines, colored left borders, inset left rails or pseudo-element left bars in product UI, notices, error panels, toasts, skeletons or documentation-style panels. The user explicitly prohibits this pattern. Avoid generic AI-styled decoration and repetitive accented cards; use spacing, typography, clear labels and restrained semantic styling instead. Preserve necessary keyboard focus outlines and ordinary symmetric control borders.
- Use the fixed frontend stack and preserve retained lockfile resolutions. Import the selected port-rust backend foundation with its source history/provenance and add one concert service.
- One canonical Auth identity, one persistent Phaser instance, and one world connection per active shell. Access tokens stay in memory; private caches are scoped by user and event.
- Virtual coordinates never imply physical arrival. Real meeting descriptions require explicit audience, revision, expiry, and reviewed place provenance.
- Enforce capacity, inventory, privacy, authorization, and idempotency on the server. Use isolated MCR databases and volumes; live-data migration is outside this task.
